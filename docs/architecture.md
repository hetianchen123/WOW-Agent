# WowAgent 三条探索线的项目结构

现有 [PLAN.md](../PLAN.md) 继续作为采集、钓鱼和售卖的实现计划。这里定义三条业务线的边界，以及从当前代码迁移到目标结构的顺序。当前仓库有合成测试，游戏内校准和真机验证仍以 [PoC 记录](poc-results.md) 为准。

## 公用底层与业务层

| 层 | 当前代码 | 目标职责 |
| --- | --- | --- |
| 游戏状态和识别 | `addon/WowAgent/`、`bot/perception/` | 插件采集和传输可读字段，Python 解码、截图、模板识别和音频。归一为带来源、采样时间、地图/场景标识的快照。领域自行声明需要哪些字段和新鲜度。 |
| 执行原语 | `bot/control/` | 输入后端、急停、移动控制和航点跟随。户外坐标与副本内定位可以有不同提供者，移动接口需要能表达定位不可用。 |
| 公用技能 | 当前分布在 `bot/modules/` 各状态 | 第二个业务出现真实复用时，在 `bot/skills/` 抽出移动到目标、交互确认、拾取、恢复等闭环。技能拥有超时、取消、失败原因和成功判据。 |
| 运行时和运维 | `bot/core/`、`bot/modules/{base,context,states_common}.py`、`bot/ops/`、`bot/cli.py` | 保留状态机、上下文注入、运行预算、停机和输入释放。暂留现有目录。将采样金币和背包满转售卖等业务逻辑与通用运行时分离。 |
| 数据和回放 | `bot/data/`、`tests/` | SQLite 事件和会话日志可共享。金币报表、SavedVariables 解析及售卖指标归赚金域。新增决策点可保存脱敏快照、候选、选择和结果供离线重放。 |
| 规划 | `bot/decision/`、`experiments/startlux/` | 任务执行器在阶段切换时请求本地 StartLux，脚本生成候选、执行选项并核验进度。异步请求期间继续检查焦点和色条，拒绝过期或不确定的结果。实验目录保留离线对照。 |

现有像素协议为每帧 20 位有效载荷，20 Hz 调度下位置 7 Hz、朝向 6 Hz，状态、背包摘要、快事件各 2 Hz。全局心跳与各字段新鲜度分别处理。任务 PoC 优先传任务 ID、目标序号、进度、交接状态及版本，文本和 NPC 关联可从本地任务数据补齐。具体字段在目标客户端逐项验证。扩协议时先锁定原消息预算、ID 位宽、分片一致性和旧版兼容测试。

## 三条业务线

| 业务 | 当前状态 | 业务自己负责 | 第一阶段验收 |
| --- | --- | --- | --- |
| 采集赚金 | `fisher.py`、`gatherer.py`、`seller.py`、`loop.py` 已有实现 | 鱼漂与上钩、节点匹配和路线、背包满交接、拍卖与邮箱、金币报表。固定流程继续用状态机。 | 在有授权的测试环境中按现有清单逐项验证。关注采集成功率、每小时净金币、停机和人工介入次数。 |
| 任务自动清理 | 同地图脚本执行器和本地 StartLux 阶段决策，实机接取待验收 | 任务依赖、跨区行程、NPC/目标关联、接取/目标达成/交付状态、恢复与检查点。 | 先验证一个 NPC 的接任务，再覆盖同区 3–5 个有依赖的任务，至少含一种计数目标和一次交付。通过动作前后快照确认进度，重启后能从检查点继续。 |
| 大秘境自动执行 | 独立研究线，有离线决策样例 | 赛季和副本路线、敌方部队进度、队伍就绪、机制与角色分工、拉怪和灭团恢复。实时打断、规避和防御由确定性机制处理。 | 先做单地图离线回放与建议模式。验证副本内定位、队伍状态、机制事件能否稳定读取，逐项统计缺失率和延迟。跟随者地下城可作为感知对照，无法验证大秘境的计时、敌方部队和组队机制。 |

初期按 `bot/modules/` 新增明确归属的业务代码。等任务闭环验证后，再考虑把赚金、任务、大秘境分别整理到 `bot/modules/{gold,quest,mythic_plus}/`。如发生移动，保留当前 CLI 模块名和配置格式。赛季或地图特定数据放在领域配置，按客户端版本或赛季标记。正式服自动控制受服务条款限制，实验与实机执行分开验收。[暴雪用户协议](https://www.blizzard.com/en-us/legal/08b946df-660a-40e4-a072-1fbde65173b1/blizzard-end-user-license-agreement)

大秘境的第一个工程问题是实时状态能否读到。《午夜》限制插件处理部分战斗状态，DBM 一类插件能显示某项信息，并不足以证明 WowAgent 能读取、编码和使用该字段。先按目标客户端版本建立字段可用性表，分别测插件可读值、界面可见值和缺失值，再选可回放的机制做验证。[暴雪关于《午夜》插件限制的说明](https://worldofwarcraft.blizzard.com/en-gb/news/24246290/combat-philosophy-and-addon-disarmament-in-midnight)

## 快环与慢环的接口

```mermaid
flowchart LR
    A[插件与视觉] --> B[带时间戳的状态快照]
    B --> C[业务规则与候选生成]
    C --> D[规则排序或本地模型]
    D --> E[检查快照和技能前置条件]
    E --> F[可取消的确定性技能]
    F --> G[控制与输入]
    F --> B
    B --> F
```

- **请求**包括 `snapshot_id`、目标、必要状态及候选。候选用稳定 ID 和由业务预先绑定的参数表示，例如 `turn_in:quest_42`。候选生成时先筛除不可执行的选项。
- **结果**包括候选 ID、置信度和放弃原因。返回时重新检查场景、关键状态时效及技能前置条件。急停、战斗事件与执行反馈继续由原控制环处理。模型超时、选项非法、状态过期时，由业务规则重算或进入暂停。
- **调度**在任务完成、换区、路线受阻、队伍就绪变化等事件上触发。调用由独立工作进程或线程处理，控制环继续取样。一次决策只推进一个可确认的技能，结果写回状态机并记录延迟。

## 实施顺序

1. 并行完成现有采集 PoC 和 [StartLux 离线实验](startlux-poc.md)。离线实验比较固定优先级与模型对反事实样例的响应。
2. 用回放样例先定任务快照协议和技能完成条件，再实现一条同区任务线。由首个实际复用点抽出技能，接入模型的初始模式为影子决策。
3. 用真实任务回放对比规则和模型的进度、误选、回退率和延迟后，决定哪些决策点值得用模型。大秘境并行做可观测性调查，能稳定确认位置、机制和队伍状态后再做单图回放闭环。
